# Qyro Engine

Después de crear y ejecutar un proyecto con el CLI, puedes aprender qué utiliza tu código dentro de la aplicación. **Qyro Engine** es ese motor: conecta configuración, archivos, entorno y framework gráfico para preparar el arranque y ofrecer servicios comunes durante la ejecución.

Se instala como `qyro-engine` y se importa como `qyro`. El CLI lo utiliza como dependencia del proyecto; al construir una entrega, el motor acompaña a la aplicación empaquetada.

## Qué prepara el motor

El arranque necesita saber cómo se llama la aplicación, qué toolkit utiliza y dónde están sus archivos. El Engine reúne esos datos y conecta un adaptador para el framework elegido.

Un **adaptador** convierte operaciones comunes del Engine —crear la aplicación nativa, iniciar su loop o aplicar un título— en llamadas al toolkit concreto. La interfaz y sus eventos continúan siendo responsabilidad de Qt, Tkinter o Kivy.

| Servicio | Para qué sirve |
| --- | --- |
| `ApplicationContext` | Reunir los servicios del arranque y exponerlos al código |
| Settings | Leer configuración y metadatos desde `settings/` |
| Resources | Localizar archivos de `resources/` mediante nombres consultables |
| Entorno | Identificar plataforma y ejecución desde código o artefacto empaquetado |
| Adaptador UI | Preparar la aplicación nativa y conectar su bucle de eventos |
| `Component` | Organizar la construcción de widgets mediante hooks |
| Telemetría | Instalar el manejo de excepciones configurado |

## El contexto de aplicación

En la primera aplicación utilizaste:

```python
from qyro import ApplicationContext

context = ApplicationContext(framework="pyside6", enable_sentry=False)
print(context.metadata.app_name)
```

El contexto selecciona el framework y prepara el motor. En Qt debe existir la aplicación nativa antes del primer widget; crear el contexto al principio proporciona ese orden. Sus propiedades y métodos permiten consultar settings, metadatos, plataforma y recursos sin reconstruir esos servicios en cada módulo.

La guía [ApplicationContext](/es/application-context) desarrolla su inicialización y uso. Después puedes utilizar [Component](/es/components) para organizar widgets reutilizables mediante etapas de construcción.

## Configuración y recursos tienen papeles distintos

Settings proporciona **valores**: por ejemplo, dimensiones iniciales o una opción de tema. Resources proporciona **rutas de archivos**: por ejemplo, un texto o stylesheet que tu código abre y utiliza. Leerlos no aplica automáticamente su contenido a la UI; tu aplicación decide qué hacer con ellos.

Ambos parten de la estructura que preparó el CLI. Comienza por [Settings](/es/settings) y [Resources](/es/resources) antes de estudiar sus reglas avanzadas.

## Desarrollo y aplicación empaquetada

Durante el desarrollo, `qyro start` ejecuta archivos Python: ese modo se llama **source**. Después de `qyro build`, el usuario ejecuta un artefacto que incluye la aplicación y sus dependencias: ese modo se llama **frozen**.

La ubicación de los archivos cambia entre los dos modos. El Engine detecta el entorno y adapta la resolución de settings y resources. No ejecuta el build: ese trabajo ya lo hizo el CLI. La guía [Source y frozen](/es/source-frozen) explica las rutas cuando necesites investigar una distribución.

## Recorrido del motor

Estudia contexto, componentes, settings y resources; después sigue el framework que utiliza tu aplicación. Las guías de secrets, protección y telemetría desarrollan necesidades específicas. Arquitectura y referencia son material de consulta para profundizar, una vez comprendido el uso habitual.

Cuando necesites coordinar estado que cambia entre varias vistas, continúa con [Manejo de estado con Pydux](/es/pydux). Es una integración independiente y opcional. Las [demos](/es/examples) reúnen los conceptos en aplicaciones ejecutables.
