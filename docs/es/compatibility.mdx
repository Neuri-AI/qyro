# Compatibilidad y limitaciones

Un adaptador implementado, una dependencia instalable y una aplicación distribuible son niveles distintos. Esta página describe el código auditado, no una garantía universal basada en una tabla del README.

## Python y toolkits

Engine y CLI declaran Python `>=3.10,<3.16`; consulta los límites adicionales de [Instalación](/es/installation). PySide2 tiene adaptador real y hooks del CLI, pero su extra del Engine requiere Python menor que 3.11. PyQt5 se declara para `>=3.11,<3.14`. El README presenta resultados más amplios: esas afirmaciones no cambian los marcadores.

La auditoría utilizó Windows y Python 3.13.16 en Conda `playground`. PyQt6 y PySide2 no estaban instalados: sus ejemplos se revisaron contra los adaptadores y compilaron sintácticamente, sin declarar ejecución gráfica local. Los detalles están en el [informe](/es/audit-report).

## Plataformas

`PlatformDetector` identifica Windows (`sys.platform` comienza con `win`), macOS (`darwin`), Linux y valores que comiencen con `android`. Android puede presentarse como Linux en algunos intérpretes; el detector no implementa otra heurística. `PlatformType.IOS` existe, pero no hay rama que lo produzca. Los demás sistemas resultan `UNKNOWN`.

Ubuntu, Fedora y Arch/Manjaro se consultan en `/etc/os-release`; GNOME/KDE en `XDG_CURRENT_DESKTOP`. No hay detección de arquitectura CPU en el detector, pese al comentario de su módulo.

## Móvil y otros entornos

El CLI acepta scaffolding iPhone/Android y declara un extra `mobile` con Buildozer. `BuildCommand` busca `mobile_build_use_case`, pero el contenedor no lo configura. `qyro build --target android` o `ios` devuelve error. No existe un flujo móvil completo conectado en el checkout.

`ExecutionMode.EMBEDDED` no lo produce el detector. Frozen genérico ofrece detección y rutas básicas, no una validación específica para cada congelador alternativo.

## Límites del runtime

- La primera inicialización fija el contexto global; no existe reset público ni cambio de toolkit.
- Settings se combina superficialmente, sin schema, persistencia ni hot reload público.
- Un toolkit importable no implica una pantalla o OpenGL utilizables.
- `Component` tiene hooks síncronos, sin reconciliación reactiva ni unmount automático.
- QSS y `resizeEvent` son integraciones Qt; Tkinter/Kivy requieren sus mecanismos nativos.
- `get_resource` no limita las rutas a un sandbox; valida entradas no confiables antes de consultarlas.
- Iconos, títulos y estilos silencian varios errores; un booleano verdadero de icono no garantiza su visualización.
- La protección no oculta absolutamente datos al cliente ni obliga a abortar ante cualquier manipulación.

## Límites del tooling

- `init` necesita plantillas externas o caché; no hay fallback incluido en este checkout.
- `start` no activa automáticamente entornos Poetry/uv ni implementa watcher.
- Build usa PyInstaller/Cython locales; `--target` no proporciona compilación cruzada.
- El CLI puede requerir Pillow aun sin instalar `desktop`.
- `clean` no retira `.qyro`, caché de plantillas ni extracción protegida.
- No separa automáticamente secretos del tooling y del cliente.
- Bundle copia resources source por defecto; puede requerir `--no-resources`.
- No hay comandos registrados de publicación, despliegue remoto, subida o test.

## Evidencia de tests y workflows

Las suites prueban APIs y adapters, muchas veces con dobles; no prueban cada escritorio y binding. El workflow de matriz del CLI enumera Windows, macOS y Linux, Python 3.10–3.13 y PySide6, PyQt6, PyQt5, Kivy y Tkinter. No incluye PySide2 ni Python 3.14 en el YAML auditado. Omite además `start` para Kivy en Windows/macOS. No se reproduce como garantía la afirmación general del README de todas las etapas en todas las celdas; los resultados remotos no se verificaron aquí.

Construye y prueba en cada sistema de destino, distribuye el artefacto completo y comprueba las funciones reales de tu aplicación. Los pendientes de diseño están en [Auditoría](/es/audit-report).
