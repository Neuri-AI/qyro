# Frameworks

Los adaptadores implementan `IUIFrameworkPort`, de modo que el resto del runtime no depende directamente de un toolkit.

## Selección

La prioridad es:

1. argumento `framework` de `ApplicationContext`/`framework_name` de `EngineContainer`;
2. clave `binding` de settings;
3. clave `framework` de settings;
4. autodetección.

La autodetección prueba:

```text
PySide6 → PyQt6 → PySide2 → PyQt5 → Kivy → Tkinter → Headless
```

Los nombres no distinguen mayúsculas y eliminan espacios externos. Un nombre desconocido genera `FrameworkNotAvailableError` con la lista admitida. Un nombre conocido pero no instalado produce el mismo tipo de error con una sugerencia de instalación.

```python
ctx = ApplicationContext(framework="pyside6")
```

Para fijarlo en configuración:

```json
{"binding": "pyside6"}
```

## Contrato común

Cada adaptador expone:

- `framework_name`
- `is_available()`
- `create_application(argv=None)`
- `run()`
- `exit(code=0)`
- `set_application_icon(path)`
- `set_window_icon(window, path)`
- `set_window_title(window, title)`

Las tres operaciones visuales retornan `bool` y son best-effort.

## Qt: PySide6, PyQt6, PySide2 y PyQt5

`BaseQtAdapter` reutiliza `QApplication.instance()` o crea una nueva con `argv`/`sys.argv`. `run()` prefiere `exec()` y cae a `exec_()` para Qt 5. `exit()` llama `QApplication.exit(code)`.

Al crear iconos, detecta el binding real del objeto objetivo por su MRO. Esto evita mezclar `QIcon` de PyQt con widgets PySide, una causa común de warnings, símbolos duplicados y crashes nativos.

Los adaptadores PySide6 y PyQt6 pueden cargar perezosamente `QApplication`. PySide2 y PyQt5 lo resuelven en el constructor si el paquete está disponible.

## Kivy

`create_application()` intenta devolver `App.get_running_app()`; si todavía no existe retorna `None`. `run()` busca de nuevo y, si es necesario, crea un `GenericKivyApp`.

- `exit()` llama `stop()`.
- título e icono se asignan como atributos si existen.
- el código de salida siempre es `0`.

La integración funciona mejor cuando tu clase principal hereda de `kivy.app.App` y controla `build()`.

## Tkinter

`create_application()` reutiliza `tkinter._default_root` y no crea una ventana inmediatamente. `ApplicationContext` puede enlazar la propia instancia cuando detecta `mainloop`.

`run()` crea `tk.Tk()` si aún no existe y ejecuta `mainloop()`. `exit()` usa `destroy()`.

Para iconos:

- `.ico` usa `iconbitmap()` cuando está disponible;
- otros formatos usan `PhotoImage` + `iconphoto()`;
- la imagen se guarda en `_qyro_icon_photo` para evitar que el garbage collector la destruya.

## Headless

Siempre está disponible y es el fallback final. `HeadlessApplication` conserva `argv`; `exec()` y `exec_()` retornan `0`. El adaptador registra los títulos e iconos aplicados en memoria, útil para tests.

```python
ctx = ApplicationContext(framework="headless", argv=["app", "--test"])
assert ctx.run() == 0
```

## Añadir un adaptador

1. Implementa `IUIFrameworkPort` o hereda de `BaseUIFrameworkAdapter`.
2. Evita importar el toolkit en el nivel del módulo si es opcional.
3. Registra el nombre en `FrameworkFactory._FRAMEWORK_REGISTRY`.
4. Decide su posición en la lista de autodetección.
5. Añade tests para disponibilidad, singleton, run/exit, título e icono.
