This page describes the options that Qyro CLI interprets when running `start`, `build`, `bundle`, and `sign`. It also clarifies which ones reach Qyro Engine at runtime and which ones exist only for tooling.

<Tip>
  The easiest way to get started is [Qyro Settings Builder](https://qyro-settings-builder.up.railway.app/). Use its interface to prepare `base.json`, the platform profiles, and `release.json`; save the exported files in `settings/` and review them before the build. Create `secrets.json` locally for protected data used by the application and `sign.json` for signing/notarization. Keep both out of version control.
</Tip>

## File map

```text
my-app/
├── build.json                 # optional override exclusive to qyro build
└── settings/
    ├── base.json              # identity, entry point, and common values
    ├── windows.json           # build options for Windows
    ├── linux.json             # build options for Linux
    ├── mac.json               # build options for macOS
    ├── release.json           # release build, protection, and bundle
    ├── sign.json              # local signing/notarization; never packaged
    └── secrets.json           # protected runtime data; never versioned
```

| File | Main consumer | Purpose |
| --- | --- | --- |
| `base.json` | CLI and Engine | Common application values. |
| `windows.json`, `linux.json`, `mac.json` | CLI; the Engine reads the file for its host | Operating-system-specific differences. |
| `build.json` | `qyro build` only | Override specific to a build invocation or project. |
| `release.json` | `qyro build`, `bundle`, and `sign` | Distribution, packaging, and protection profile. |
| `sign.json` | `qyro sign` only | Certificates, identities, and signing/notarization credentials. Excluded from builds. |
| `secrets.json` | CLI and Engine | API keys and other protected data required by the application at runtime. |

<Warning>
  The Engine preserves unknown keys in `context.app_settings`, but that does not mean it executes them. `optimization`, `bundle`, `sign`, `uac`, and `resource_protection` are CLI options. Likewise, `debug` does not enable debug mode in your application code by itself.
</Warning>

## Precedence and merge

The CLI performs a **deep merge** of objects: it preserves nested keys that have not been replaced. Lists and simple values are replaced. The most important rule is simple: **the file loaded last takes precedence**.

| Command | Load order, from lowest to highest priority |
| --- | --- |
| `qyro start` | The CLI uses `base.json` → `secrets.json` to locate the binding and entry point. Inside the app, the Engine loads `base.json` → platform profile → `secrets.json` again. |
| `qyro build` | `base.json` → platform profile → selected profile (`release` by default) → `secrets.json` → `build.json` → command options. |
| `qyro bundle` | `base.json` → `release.json` → `secrets.json` → command options. |
| `qyro sign` | `base.json` → `release.json` → `sign.json` → command options. `secrets.json` remains present as application configuration, but it must not contain signing keys. |

Example: if `windows.json` defines `"bundle_mode": "onedir"` and `release.json` changes the value to `"onefile"`, the release build uses `onefile`. If `secrets.json` overrides an earlier key, `secrets.json` wins.

### Platform and profile names

For new projects, use these names:

| Platform | Recommended file | Compatible profile names |
| --- | --- | --- |
| Windows | `windows.json` | `windows`, `win32`, `win` |
| Linux | `linux.json` | `linux`, `linux2`, `gnu` |
| macOS | `mac.json` | `mac`, `macos`, `darwin`, `osx` |

`macos.json` is preserved as a compatible alias; if both `macos.json` and `mac.json` exist, the latter takes precedence. You can also create your own profile, for example `staging.json`, and select it with `qyro build --profile staging`.

<Note>
  On Windows, you do not need to duplicate the release configuration inside `windows.json`. Keep Windows-specific differences in `windows.json`, distribution options in `release.json`, signing in `sign.json`, and runtime secrets in `secrets.json`.
</Note>

The Engine uses a different rule and performs a **shallow merge**:

| Mode | Secrets used |
| --- | --- |
| Development/source | Reads the plain `settings/secrets.json` file. |
| Frozen application | Reads and decrypts in memory the encrypted payload generated by `qyro build`. |
| Both available | Applies the plain file first and then the encrypted payload; encrypted values take precedence. |

The Engine's complete order is `base.json` → first valid platform profile → plain secrets → encrypted secrets. Because the merge is shallow, if you override a nested object in a profile or in `secrets.json`, repeat the entire object. See [Engine settings](/en/settings).

Invalid JSON files or files whose top level is not an object are silently ignored when loading CLI profiles. Validate files before a release; do not rely on that silence as a fallback mechanism.

## `base.json`

Complete example:

```json
{
  "app_name": "MyApp",
  "author": "Qyro",
  "entry_point": "main.py",
  "addons": [],
  "version": "1.0.0",
  "binding": "PySide6",
  "icon": "resources/custom/app.ico",
  "hidden_imports": [
    "__future__",
    "PySide6.QtCore",
    "PySide6.QtGui",
    "PySide6.QtWidgets"
  ]
}
```

The `icon` path is an example. Change it if your icon is located elsewhere.

### Identity and startup

| Key | Type | Build default | Meaning |
| --- | --- | --- | --- |
| `app_name` | non-empty string | folder name | Name of the executable, bundle, and metadata. The Engine also uses it as the visible name. |
| `author` | string | `Developer` | Author or publisher. Used for metadata and to suggest a macOS bundle ID. |
| `version` | string | `1.0.0` | Version used in names and packages. The build does not require SemVer, although it is the recommended convention. |
| `entry_point` | path string | `main.py` | Entry Python script, relative to the root unless absolute. `qyro start` requires it to exist. |
| `binding` | string | `PySide6` | Toolkit: `PySide6`, `PyQt6`, `PyQt5`, `PySide2`, `Kivy`, or `Tkinter`; parsing is case-insensitive. |
| `icon` | path string | no explicit icon | Icon passed to PyInstaller. The build CLI does not use `app_icon` as an alias, although the Engine recognizes it. |
| `freeze_dir` | path string | `build` | Folder searched by `clean`, `bundle`, `sign`, and their guards. The current freezer always writes to `build`; do not change this value until both paths are connected. |
| `identifier` | string | `com.qyro.app` in Engine | Engine metadata. For the `.app`, use `mac_bundle_identifier`. |
| `description` | string | empty in Engine | Metadata available to your application; the current packager does not include it automatically. |

`qyro start` needs `binding` and `entry_point` in the loaded settings. `qyro build` does apply the defaults in the table, so an incomplete file might build but fail to start through `qyro start`.

### Imports, addons, and custom data

| Key | Type | Effect |
| --- | --- | --- |
| `hidden_imports` | list of strings | Adds one `--hidden-import` per module. Use it for dynamic imports that PyInstaller does not detect. |
| `addons` | list | The template stores the selected addons and the Engine can expose the value. In the current build it is not copied to `FreezeManifest`, so it does not enable additional hooks by itself. |
| any other key | any JSON | The Engine preserves it in `context.app_settings`; the CLI ignores it if no use case recognizes it. |

Framework hooks already include the essential modules for the active binding and exclude competing bindings. Therefore, `PySide6.QtCore`, `QtGui`, and `QtWidgets` are usually redundant in `hidden_imports`; they are harmless and can make the intent explicit. Add modules such as `PySide6.QtSvg` only if you actually use them and they are not being detected.

## Platform profiles

The three profiles share `bundle_mode`, `paths`, `collect_all`, `debug`, and `optimization`. Windows adds `uac`; macOS adds `mac_bundle_identifier`.

### Common options

| Key | Type / values | Default | Actual effect |
| --- | --- | --- | --- |
| `bundle_mode` | `onedir` or `onefile` | `onedir` | PyInstaller format. It also accepts `bundle` and `single` as aliases for `onefile`; any other value falls back to `onedir`. |
| `paths` | list of paths | `[]` | Each item is passed as `--paths`; helps resolve modules or binaries outside the normal path. |
| `collect_all` | list of packages | `[]` | Each package is passed as `--collect-all`, including code, data, and binaries found by PyInstaller. Increases size. |
| `hidden_imports` | list of modules | `[]` | Concatenated with the `build.json` list and deduplicated. |
| `extra_args` | list of strings | `[]` | Advanced arguments passed to PyInstaller. The `extra_pyinstaller_args` alias also exists in settings. |

Relative paths are interpreted from the project root in operations that resolve them. For reproducible builds, use paths within the repository and avoid absolute paths tied to a specific machine.

### `debug`

```json
{
  "debug": {
    "enabled": false,
    "console": false,
    "unstripped": false,
    "bootloader_debug": false
  }
}
```

| Key | Default | Effect |
| --- | --- | --- |
| `enabled` | `false` | Enables build debug mode and a console. |
| `console` | `false` | Keeps a terminal window. `console_window` is an alias. |
| `unstripped` | `false` | Prevents stripping binaries when debug is enabled. |
| `bootloader_debug` | `false` | Enables PyInstaller bootloader debugging. |

`debug.enabled` affects the build. It does not automatically configure logging, environment variables, or debug flags in your application code.

### `optimization`

The default optimization profile is:

```json
{
  "optimization": {
    "strip_binaries": true,
    "clean_build": true,
    "upx_enabled": true,
    "upx_dir": null,
    "upx_level": 9,
    "upx_excludes": [
      "vcruntime140.dll",
      "python3*.dll",
      "sdl2.dll",
      "glew32.dll",
      "kivy*.pyd"
    ],
    "exclude_binaries": [],
    "exclude_plugins": [],
    "bytecode_opt": 1,
    "remove_translations": true,
    "exclude_modules": [
      "unittest",
      "test",
      "pydoc"
    ]
  }
}
```

`exclude_binaries` and `exclude_plugins` are intentionally empty by default: Qyro cannot know which binaries or Qt capabilities your application uses. In contrast, `upx_excludes` protects runtimes that commonly fail when compressed, and `exclude_modules` removes development tools from the standard library.

| Key | Type / default | What it does |
| --- | --- | --- |
| `strip_binaries` | boolean, `true` | On Unix systems, adds `--strip` and runs `strip` again on compatible binaries. Skipped on Windows. |
| `clean_build` | boolean, `true` | Adds `--clean`, removes temporary files, `*.dist-info` metadata, translations, and some generic/Wayland Qt plugins. |
| `upx_enabled` | boolean, `true` | Allows UPX compression and a subsequent pass over binaries. Disabled on macOS. |
| `upx_dir` | path or `null` | Folder containing the `upx` binary; if it exists, it is passed to PyInstaller. |
| `upx_level` | integer `1`–`9`, default `9` | Level used by the subsequent UPX pass. An out-of-range value invalidates the manifest. |
| `upx_excludes` | list of globs; default shown above | Prevents compression of sensitive binaries. It is advisable to preserve the Python runtime, Qt Core, and C/C++ runtimes. |
| `bytecode_opt` | `0`, `1`, or `2`, default `1` | Python optimization: none, `-O`, or `-OO`. Level `2` removes docstrings. |
| `exclude_modules` | list; default `unittest`, `test`, `pydoc` | Passes `--exclude-module` and then removes related binaries/directories. |
| `exclude_binaries` | list of globs; default `[]` | Removes matches from the output after PyInstaller. |
| `exclude_plugins` | list of names/globs; default `[]` | Removes categories from the Qt plugins directory. `*` or `all` keeps only `platforms`. |
| `remove_translations` | boolean, `true` | Removes `translations` folders. `clean_build: true` also removes them even if this is set to `false`. |

```json
    ],

      "opengl32sw.dll",

      "qminimal.dll"
    ],
    "exclude_plugins": [
      "generic",
      "networkinformation",
      "tls",
      "styles",
      "platforminputcontexts",
      "iconengines",
      "imageformats"
    ],
    "bytecode_opt": 1,
    "remove_translations": true,
    "exclude_modules": [
      "PySide6.QtWebEngineCore",
      "PySide6.QtWebEngineWidgets",
      "PySide6.QtWebEngineQuick",
      "PySide6.Qt3DCore",
      "PySide6.QtQuick3D",
      "PySide6.Qt3DAnimation",
      "PySide6.QtPdf",
      "PySide6.QtMultimedia",
      "PySide6.QtSpatialAudio",
      "PySide6.QtSensors",
      "PySide6.QtBluetooth",

  }

```

<Warning>
  `exclude_modules`, `exclude_binaries`, and `exclude_plugins` are not merely suggestions for PyInstaller: Qyro performs a subsequent purge of the output. Excluding `QtNetwork`, `tls`, `imageformats`, `styles`, QML/Quick, multimedia, or OpenGL can break HTTPS, images, styles, views, or rendering. Start with the defaults, measure the size, and add one exclusion at a time together with a functional test.
</Warning>

#### What the example exclusions remove

| Entry or family | Functionality you should verify before excluding it |
| --- | --- |
| `PySide6.QtWebEngine*` | Embedded Chromium browser, advanced HTML, and WebEngine widgets/Quick. |
| `PySide6.Qt3D*`, `QtQuick3D` | 3D scenes, animation, and rendering. |
| `PySide6.QtPdf` | PDF reading and display through Qt. |
| `PySide6.QtMultimedia`, `QtSpatialAudio` | Audio, video, cameras, and spatial audio. |
| `PySide6.QtSensors`, `QtBluetooth` | Device sensors and Bluetooth. |
| `PySide6.QtCharts` | Qt Charts graphs. |
| `PySide6.QtDesigner` | Qt Designer integration/runtime and form loading that depends on it. |
| `PySide6.QtVirtualKeyboard` | Virtual/touch keyboard. |
| `PySide6.QtQml`, `QtQuick`, `QtQuickWidgets` | QML engine, Qt Quick interfaces, and their integration with widgets. |
| `PySide6.QtOpenGL`, `QtOpenGLWidgets` | OpenGL APIs and widgets. |
| `PySide6.QtSvg` | SVG reading/rendering through Qt SVG. |
| `PySide6.QtNetwork` | Qt networking, sockets, and functions that may support TLS/HTTPS. |
| `tkinter` | Tk interface and Tcl/Tk libraries; exclude it only if no dependency uses it. |
| `unittest`, `test`, `pydoc` | Standard-library development tools; usually the least risky exclusions in production. |

| Qt plugin | What becomes unavailable |
| --- | --- |
| `generic` | Generic input plugins; may affect special devices or environments. |
| `networkinformation` | Network status/connectivity detection. |
| `tls` | Qt TLS backends; may break secure connections. |
| `styles` | Additional widget styles. |
| `platforminputcontexts` | Input methods, IME, and composition for certain languages/desktops. |
| `iconengines` | Additional icon engines, including formats/themes that require them. |
| `imageformats` | Image codecs such as JPEG, GIF, WebP, or SVG depending on the installed toolkit. |

The binaries `opengl32sw.dll`, `qdirect2d.dll`, `qoffscreen.dll`, and `qminimal.dll` correspond, respectively, to the software OpenGL renderer and the Direct2D, offscreen, and minimal backends. Remove them only if the production backend cannot select them. The `platforms` folder/plugin containing `qwindows`, `qcocoa`, or `qxcb` is essential for displaying windows, and Qyro protects it during the global purge.

DLL globs from the Windows examples, such as `opengl32sw.dll`, provide no benefit on Linux or macOS. You can maintain separate profiles so each list describes binaries that actually exist on that platform.

## `windows.json`

```json
{
  "bundle_mode": "onedir",
  "paths": [],
  "collect_all": [],
  "uac": {
    "level": "asInvoker",
    "ui_access": false
  },
  "debug": {
    "enabled": false,
    "console_window": false
  },
  "optimization": {
    "strip_binaries": true,
    "clean_build": true,
    "upx_enabled": true,
    "upx_dir": null,
    "upx_level": 9,
    "upx_excludes": [
      "vcruntime140.dll",
      "python3*.dll",
      "PySide6.QtCore.pyd",
      "MSVCP140.dll",
      "Qt6Core.dll"
    ],
    "exclude_binaries": [],
    "exclude_plugins": [],
    "bytecode_opt": 1,
    "exclude_modules": ["unittest", "test", "pydoc"]
  }
}
```

### UAC control

| Key | Values | Effect |
| --- | --- | --- |
| `uac.level` | `asInvoker` | Runs with the user's permissions; default. |
|  | `highestAvailable` | The model recognizes it, but the current adapter does not emit a specific PyInstaller flag for this level. |
|  | `requireAdministrator` | Adds `--uac-admin`, and Windows will request elevation. |
| `uac.ui_access` | boolean | Adds `--uac-uiaccess`. Use it only if you understand Windows signing and installation requirements. |

`"uac": true` is also accepted to request administrator privileges, and `false` for `asInvoker`. The `qyro build --uac` flag forces administrator privileges over the JSON.

On Windows, `strip_binaries` does not run `strip`. UPX can reduce size, but some antivirus products react to compressed executables; always validate the signed artifact in the distribution environment.

## `linux.json`

```json
{
  "categories": "Utility;",
  "description": "Desktop client",
  "author_email": "dev@example.com",
  "url": "https://example.com",
  "bundle_mode": "onedir",
  "paths": [],
  "collect_all": [],
  "debug": {
    "enabled": false,
    "console": false
  },
  "optimization": {
    "strip_binaries": true,
    "clean_build": true,
    "upx_enabled": true,
    "upx_dir": null,
    "upx_level": 9,
    "upx_excludes": ["libpython3*.so*", "libQt6Core.so*", "QtCore.abi3.so"],
    "exclude_binaries": [],
    "exclude_plugins": [],
    "bytecode_opt": 1,
    "exclude_modules": ["unittest", "test", "pydoc"]
  }
}
```

`categories`, `author_email`, `description`, and `url` remain available as settings, but the current Linux packager does not transfer them to FPM. The `deb`, `rpm`, and `arch` packages mainly use `app_name`, `version`, and the `/opt/<app_name>` prefix. Do not rely on those four keys yet for the final package metadata.

`strip_binaries` and UPX can fail or damage uncommon native extensions. Keep `libpython`, Qt Core, and the binding extension in `upx_excludes`, and run the binary on a distribution matching the target.

## `mac.json`

```json
{
  "bundle_mode": "onedir",
  "paths": [],
  "collect_all": [],
  "mac_bundle_identifier": "com.qyroteam.qyrokivyapp",
  "debug": {
    "enabled": false,
    "console": false
  },
  "optimization": {
    "strip_binaries": true,
    "clean_build": true,
    "upx_enabled": false,
    "exclude_binaries": [],
    "exclude_plugins": [],
    "bytecode_opt": 1,
    "exclude_modules": ["unittest", "test", "pydoc"]
  }
}
```

| Key | Meaning |
| --- | --- |
| `mac_bundle_identifier` | Reverse-DNS identifier passed to PyInstaller. `bundle_identifier` is an alias. If missing, Qyro suggests one based on the author and name. |
| `sign.mac.target_architecture` | Architecture passed to the macOS build. `universal2` requires universal dependencies; the current flow may downgrade it to the native architecture with a warning. |

<Warning>
  **UPX is not recommended on macOS.** Compressing binaries can cause startup failures, invalidate code signing, and cause notarization or Gatekeeper checks to fail. Keep `upx_enabled: false` in signed release builds.
</Warning>

The current adapter keeps UPX disabled on macOS even if `upx_enabled` is `true`, but you should keep the explicit `false` value to document the intent and avoid depending on that internal behavior. After modifying the `.app`, Qyro applies an ad hoc signature; for distribution, use `qyro sign` with a valid Developer ID identity.

## `build.json`

`build.json` lives at the root, not inside `settings/`, and is **optional**. For new projects, configure the build and its optimizations in `settings/<platform>.json`; reserve `build.json` for exceptional overrides strictly tied to the freezer:

```json
{
  "entry_point": "src/main.py",
  "platform": "windows",
  "bundle_mode": "onefile",
  "icon": "resources/base/app.ico",
  "hidden_imports": ["my_app.plugins.pdf"],
  "paths": ["vendor"],
  "collect_all": ["babel"],
  "extra_args": ["--log-level", "WARN"],
  "resource_protection": {
    "enabled": true,
    "settings_dir": "settings",
    "resources_dir": "resources",
    "bundle_path": ".qyro/resources.pak"
  }
}
```

The top level must be a JSON object. If the syntax is invalid, the CLI displays a warning and continues with settings; a list, string, or other type at the top level is not a supported manifest.

### Recognized keys

| Group | Keys |
| --- | --- |
| Identity and entry | `app_name`, `author`, `version`, `entry_point`, `binding` |
| Platform and format | `platform`, `bundle`, `bundle_mode` |
| Behavior | `uac`, `debug`, `optimization` |
| PyInstaller | `hidden_imports`, `icon`, `extra_args`, `paths`, `collect_all` |
| macOS | `mac_bundle_identifier`, `bundle_identifier` |
| Protection | `resource_protection`, `resources` |

In `build.json`, `bundle` is a string alias for `bundle_mode` and must contain `"onedir"` or `"onefile"`. It is not the `bundle` object from `release.json`, which configures DMG, NSIS, and additional files.

### Actual precedence

`build.json` is not merged uniformly with settings. The rule depends on the field type:

| Field type | Behavior |
| --- | --- |
| Scalars such as `app_name`, `author`, `version`, `entry_point`, `binding`, `icon`, and bundle ID | A non-empty value from `build.json` wins. If it is `null`, `false`, or an empty string, the code may fall back to the settings value because it uses `or`. |
| `platform` | Taken directly from `build.json` when the key exists. It must be a valid platform string. |
| `uac`, `debug`, `optimization` objects | A non-empty object from `build.json` replaces the entire settings object. Missing internal keys use CLI defaults; they are not completed from the settings object. |
| `resource_protection` / `resources` | The first truthy value between both aliases and settings is used. To disable an active configuration, use `{"enabled": false}`; a direct `false` may fall back to the settings value. |
| Lists | Concatenated as explained in the following table. |

This use of `or` also affects direct booleans. To disable values that are active in settings, use explicit objects:

```json
{
  "uac": {
    "level": "asInvoker",
    "ui_access": false
  },
  "debug": {
    "enabled": false,
    "console": false
  },
  "resource_protection": {
    "enabled": false
  }
}
```

### Combining lists

| List | Result |
| --- | --- |
| `hidden_imports` | Items from `build.json` + items from settings; duplicates are removed while preserving order. |
| `paths` | Items from `build.json` + items from settings; duplicates are not removed. |
| `collect_all` | Items from `build.json` + items from settings; duplicates are not removed. |
| `extra_args` | Items from `build.json` + `extra_pyinstaller_args` or `extra_args` from settings; duplicates are not removed. On macOS, signing and architecture arguments may be added afterward. |

### Command options

When provided, `--mode`/`--onefile`, `--debug`, `--console`, `--uac`, and `--clean` take precedence over the manifest. `--debug`, `--console`, `--uac`, and `--clean` are activation flags: the current parser does not provide `--no-debug`, `--no-console`, `--no-uac`, or `--no-clean` to force `false`.

`--target` selects the platform profile before reading `build.json`; `--profile` selects another profile, `release` by default. The `build.json.platform` value changes the manifest target, but it does not automatically load another platform's JSON or provide cross-compilation. Build Windows on Windows, macOS on macOS, and Linux on Linux using their native toolchains.

## `release.json`

This file is a CLI profile. The Engine does not automatically load it when your app starts. It can contain release build, protection, and bundle options:

```json
{
  "bundle_mode": "onedir",
  "resource_protection": {
    "enabled": true,
    "settings_dir": "settings",
    "resources_dir": "resources",
    "bundle_path": ".qyro/resources.pak"
  },
  "bundle": {
    "dmg": {
      "window": {"x": 200, "y": 120},
      "window_size": {"width": 660, "height": 420},
      "icon_size": 120,
      "app_position": {"x": 180, "y": 180},
      "applications_position": {"x": 480, "y": 180},
      "background": "assets/dmg-background.jpg",
      "extra_files": [
        "README.md",
        {
          "source": "docs/RELEASE_NOTES.md",
          "destination": "docs/RELEASE_NOTES.md"
        }
      ]
    },
    "nsis": {
      "icons": {
        "install": "resources/base/install.ico",
        "uninstall": "resources/base/uninstall.ico"
      },
      "welcome_bitmap": "resources/base/welcome.bmp",
      "install_location": "programfiles64",
      "execution_level": "highest"
    }
  }
}
```

Keys such as `"release": true` or `"environment": "production"` may be useful to your application, but the current bundle/signing use cases do not assign behavior to them.

Because `release.json` is merged before the manifest is built, it can also override common build fields such as `bundle_mode`, `debug`, `optimization`, `paths`, `collect_all`, `hidden_imports`, `icon`, or `resource_protection`. `bundle` is interpreted only by its use case; signing lives in `sign.json`.

### `resource_protection`

| Key | Default | Meaning |
| --- | --- | --- |
| `enabled` | `false` | Packages `settings/` and `resources/` into an encrypted container and compiles the runtime secret module. |
| `settings_dir` | `settings` | Source configuration folder. |
| `resources_dir` | `resources` | Source resources folder. |
| `bundle_path` | `.qyro/resources.pak` | Internal path of the protected package. |

`resources` is an alias. Even without full protection, the current build compiles the runtime to protect `secrets.json`; you need Cython and a C compiler. Read [Protected resources](/en/protected-resources) before considering this a security boundary.

### `bundle.extra_files`

A string entry copies the file or folder to the root of the distribution. An object entry uses:

| Key | Required | Rule |
| --- | --- | --- |
| `source` | yes | Existing path, relative to the project or absolute. |
| `destination` | no | Relative path inside the bundle. It cannot be absolute or escape using `..`. |

Run `qyro bundle --check` to validate sources and destinations without generating the package.

Files are copied to the general `release/<app_name>/` staging area. Therefore, they are included in formats that package that staging area, such as `dir`, `zip`, and `tar.gz`. Use `bundle.dmg.extra_files` when a file must appear inside a DMG.

### `bundle.dmg`

| Key | Shape | Effect |
| --- | --- | --- |
| `window` | `{x, y}` | Initial window position. |
| `window_size` | `{width, height}` | Window size. |
| `icon_size` | positive integer | Icon size. |
| `app_position` | `{x, y}` | Position of the `.app`; `app_icon_position` is an alias. |
| `applications_position` | `{x, y}` | Position of the Applications link; `app_drop_link` is an alias. |
| `background` | path | Existing background image. |
| `extra_files` | list | Files or directories placed at the DMG root. Uses the same string/object forms as `bundle.extra_files`. |

`bundle.dmg.extra_files` is copied to the dedicated DMG staging directory and included in the image when `create-dmg` is available. It is not supported by `hdiutil`; Qyro rejects that configuration rather than creating a DMG without the requested files.

Any customization requires `create-dmg`. Without customization, Qyro prefers `create-dmg` and can use `hdiutil` as a fallback on macOS.

### `bundle.nsis`

| Key | Values / default | Effect |
| --- | --- | --- |
| `icons.install` | path; default `resources/base/install.ico` if it exists | Installer icon. If you declare the key, the file is required. |
| `icons.uninstall` | path; default `resources/base/uninstall.ico` if it exists | Uninstaller icon. If you declare the key, the file is required. |
| `welcome_bitmap` | optional path | Welcome/completion bitmap; if declared, it must exist. |
| `install_location` | `programfiles64`, `programfiles32`, `appdata`; default `programfiles64` | Base installation folder. |
| `execution_level` | `highest`, `admin`, `user`; default `highest` | Level requested by the NSIS installer. |

NSIS requires `makensis`. The installer level is independent of the executable's `uac`.

## `sign.json`

This local profile contains all configuration exclusive to `qyro sign`. The CLI loads it after `release.json`. The Engine does not read it, and the CLI excludes it from both ordinary PyInstaller data and the protected resources package.

```json
{
  "sign": {
    "windows": {
      "certificate": "src/sign/windows/certificate.pfx",
      "password": "CertificatePassword",
      "timestamp_server": "https://timestamp.digicert.com",
      "description": "QyroApp",
      "url": "https://example.com"
    },
    "mac": {
      "identity": "Developer ID Application: Example (TEAMID)",
      "entitlements": "src/sign/mac/entitlements.plist",
      "notary": {
        "enabled": true,
        "staple": true,
        "assess_gatekeeper": true,
        "keychain_profile": "QYRO-NOTARY"
      }
    }
  }
}
```

Add `settings/sign.json`, certificates, and private keys to `.gitignore`. In CI, generate or mount these files from the secret store immediately before signing.

### `sign.windows`

| Key | Required | Meaning |
| --- | --- | --- |
| `certificate` | yes | PFX/P12 file for Authenticode. Legacy default: `src/sign/windows/certificate.pfx`. |
| `password` | yes | Certificate password, stored locally in `sign.json`. |
| `timestamp_server` | no | RFC 3161/Authenticode server used by `signtool`. |
| `description` | no | Signed description; default `app_name`. |
| `url` | no | Informational URL included in the signature. |

`qyro sign` scans `.exe`, `.cab`, `.dll`, `.ocx`, `.msi`, and `.xpi` inside the output. It requires Windows and `signtool`.

### `sign.mac`

| Key | Meaning |
| --- | --- |
| `identity` | Identity available in Keychain for `codesign`. |
| `entitlements` | Plist file used during signing. |
| `notary.enabled` | Enables submission with `notarytool`. |
| `notary.staple` | Attaches the ticket after notarization; default `true`. |
| `notary.assess_gatekeeper` | Runs Gatekeeper assessment; default `false`. |

Configure exactly one notarization authentication method:

1. `notary.keychain_profile`;
2. `notary.key_path` + `notary.key_id` and, if applicable, `notary.issuer`;
3. `notary.apple_id` + `notary.team_id` + `notary.app_password`.

The `--notarize`, `--staple`, `--no-assess`, and `--keychain-profile` flags can override these options for an invocation.

### Legacy signing keys

For older projects, the CLI preserves flat aliases inside `sign.json`: `windows_sign_certificate`, `windows_sign_pass`, `windows_sign_server`, `windows_sign_description`, `mac_sign_identity`, `mac_sign_entitlements`, `mac_sign_notarize`, `mac_sign_staple`, `mac_sign_assess`, `mac_sign_notary_profile`, `mac_sign_notary_key`, `mac_sign_notary_key_id`, `mac_sign_notary_issuer`, `mac_sign_apple_id`, `mac_sign_team_id`, and `mac_sign_app_password`. The `sign.windows` and `sign.mac` structures are the recommended form. `mac_target_architecture` is a build option and belongs in `mac.json`.

## `secrets.json`

This file contains API keys, tokens, licenses, and other protected data required by the application at runtime. It must be a JSON object and is applied as an override:

```json
{
  "api_url": "https://api.example.com",
  "api_key": "clave-de-la-aplicacion",
  "service_token": "token-protegido",
  "license_key": "licencia-local"
}
```

In source mode, the Engine reads the local JSON. During `qyro build`, the CLI excludes the plain file, encrypts the entire object with AES-256-GCM, and stores `.qyro/secrets.enc` inside `resources.pak`; the compiled runtime module allows the Engine to authenticate, decrypt, and merge it in memory. The application accesses the values through `context.app_settings` or `self.app_settings` in the same way in both modes.

The Engine performs a shallow merge: if your application uses nested objects, repeat the entire object in `secrets.json` or use flat keys. The CLI performs a deep merge. Do not add a `sign` object or flat signing aliases: the build rejects them to prevent those credentials from entering the client. Signing and notarization belong exclusively in `sign.json`.

<Note>
  `secrets.json` travels encrypted with the application; `sign.json` is never packaged. This separation prevents accidentally distributing certificate passwords, identities, or notarization credentials.
</Note>

Practical rules:

- add `settings/secrets.json` to `.gitignore` and check with `git status` before every commit;
- also add `settings/sign.json` to `.gitignore`;
- use `{}` if the first build without protection requires the file and the app has no secrets;
- use `secrets.json` for sensitive values and keep it out of version control;
- do not print the settings dictionary in logs;
- remember that values are decrypted in memory when the app uses them; for high-value secrets, apply minimum scope, rotation, and short-lived tokens.

See [Secrets](/en/secrets) for source/frozen loading, Engine precedence, and the encrypted format.

## Recipes

### Conservative PySide6 application

Start without aggressive purges:

```json
{
  "bundle_mode": "onedir",
  "debug": {"enabled": false, "console": false},
  "optimization": {
    "clean_build": true,
    "strip_binaries": false,
    "upx_enabled": false,
    "bytecode_opt": 1,
    "remove_translations": false,
    "exclude_modules": [],
    "exclude_binaries": [],
    "exclude_plugins": []
  }
}
```

Test the executable; then enable one optimization at a time. `onedir` makes it easier to inspect which file is missing and is usually better during diagnostics. Switch to `onefile` at the end if startup time and temporary extraction are acceptable.

### Missing dynamic import

If it works in source mode but `ModuleNotFoundError` appears in the executable:

```json
{
  "hidden_imports": ["my_app.plugins.csv_export"],
  "collect_all": ["plugin_with_data_files"]
}
```

Use `hidden_imports` for dynamically imported code and `collect_all` when the package also requires data or binaries.

### Verifiable distribution workflow

```bash
qyro build --target windows
qyro sign --check --platform windows
qyro sign --platform windows
qyro bundle --check --platform windows --format nsis
qyro bundle --platform windows --format nsis
```

Change the platform and format on the corresponding host. `bundle` does not sign automatically, and `sign` does not create the installer.

## Checklist before publishing

- `entry_point`, `icon`, certificates, entitlements, backgrounds, and extra files exist.
- The JSON binding matches the one installed in the environment running Qyro CLI.
- The build was created on the same target operating system.
- Exclusions were tested with HTTPS, images, styles, printing, multimedia, and any optional feature used.
- `qyro bundle --check` and `qyro sign --check` complete successfully.
- The final executable starts on a clean machine, not only in the development environment.
- `settings/secrets.json` and `settings/sign.json` are not versioned, and the runtime payload does not contain signing credentials.
