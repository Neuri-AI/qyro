# Internal architecture

Qyro uses a practical Clean Architecture layout. Infrastructure depends on application contracts and domain objects; `EngineContainer` wires concrete implementations together.

```text
┌───────────────────────────────────────────────────────────┐
│ Client: ApplicationContext, Component, qyro.* helpers     │
├───────────────────────────────────────────────────────────┤
│ Application: use cases and abstract ports                 │
├───────────────────────────────────────────────────────────┤
│ Domain: entities, value objects, enums, errors            │
├───────────────────────────────────────────────────────────┤
│ Adapters: OS, JSON, filesystem, GUI, telemetry, crypto    │
└───────────────────────────────────────────────────────────┘
                  EngineContainer wires them
```

## Domain

The domain has no GUI or filesystem dependencies. It defines `PlatformType`, `ExecutionMode`, `ResourceQuery`, `ResourceResult`, `AppMetadata`, and the Qyro error hierarchy.

## Application

| Port | Capability |
| --- | --- |
| `IEnvironmentPort` | platform, mode, root, bundle |
| `ISettingsPort` | raw configuration and metadata |
| `IResourcePort` | resolve and list resources |
| `IUIFrameworkPort` | native app, event loop, title, icon |
| `ITelemetryPort` | install and handle uncaught exceptions |

Use cases are intentionally small:

- `ResolveResourceUseCase` normalizes queries and enforces `required`.
- `LoadSettingsUseCase` caches metadata and reads individual values.
- `InitializeEngineUseCase` validates the toolkit, installs telemetry, loads metadata, creates the native app, and returns boot information.

## Composition root

`EngineContainer` creates environment, settings, and resource adapters; reads settings to choose telemetry; selects the framework; then constructs the three use cases.

```python
EngineContainer(
    framework_name=None,
    custom_root=None,
    custom_resources_dir=None,
    custom_settings_dir=None,
    enable_sentry=True,
)
```

Construction alone does not run initialization. `ApplicationContext._ensure_global_engine()` executes the initialize use case.

Boot information contains the native app, metadata, platform, execution mode, and frozen flag, which the context exposes as properties.

## Environment detection

Truthy `sys.frozen` means frozen. `_MEIPASS` produces `FROZEN_PYINSTALLER`; other frozen builds produce `FROZEN_GENERIC`. Source mode walks upward for `pyproject.toml` or `src/`.

`PlatformDetector` maps `sys.platform` and can detect Ubuntu, Fedora, Arch/Manjaro, GNOME, and KDE. iOS and embedded mode exist as domain values but are not automatically emitted by current adapters.

## Design consequences

- A process-wide singleton matches GUI toolkits but makes the first initialization authoritative.
- Visual operations are best-effort to tolerate toolkit differences.
- Authenticated-secret failures are strict.
- Protected resources are extracted so public APIs can continue returning filesystem paths.
- Shallow configuration merging is predictable but requires complete nested overrides.

Ports can be instantiated with fakes in unit tests; the current container itself constructs concrete adapters rather than accepting injected instances.
