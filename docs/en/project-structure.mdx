title: "Project structure"
description: "Understand the project generated by Qyro CLI and its settings and resources directories."
---

Qyro CLI creates the initial project through `qyro init`. The selected template provides code, dependencies, and configuration; from there, you develop within that structure.

There are two main directories for application data: **`settings/` for configuration** and **`resources/` for input files**.

```text
my-app/
├── pyproject.toml
├── main.py                 # or the template's entry_point
├── settings/
│   ├── base.json
│   ├── windows.json         # optional
│   ├── mac.json             # optional
│   ├── linux.json           # optional
│   ├── release.json         # distribution profile
│   ├── sign.json            # local signing/notarization; not packaged
│   └── secrets.json         # protected runtime data
├── resources/
│   ├── base/
│   ├── windows/             # optional
│   ├── mac/                 # optional
│   └── linux/               # optional
├── views/                   # organization the template may add
└── components/              # organization the template may add
```

The tree shows the usual organization; templates may add their own modules and assets. Optional directories are used when your application needs platform-specific differences.

## Code and dependencies

`pyproject.toml` describes the project and its dependencies. The file specified by `entry_point` in settings starts the application. Additional modules contain views, components, and your own logic: organize them according to the needs of the generated project.

The CLI uses this data to run and build the application. You do not have to move its configuration into the code every time you call `qyro start`.

## `settings/`: configuration

`base.json` contains the common values: name, version, author, binding, and entry point, along with options your application needs to read.

The platform JSON files allow you to define differences for Windows, macOS, or Linux. `release.json` contains tooling options for preparing distributions. `sign.json` is exclusively for signing/notarization and the CLI excludes it from the build. `secrets.json` contains protected data that the application needs at runtime. Both local files must remain outside version control. The [CLI file reference](/en/configuration-files) explains all their fields; runtime merging and secret handling are covered in [Settings](/en/settings) and [Secrets](/en/secrets).

## `resources/`: application files

Store text, images, fonts, styles, templates, and other assets here. `resources/base/` contains common files; the platform directories contain variants when you need them.

Your code accesses those files through the Engine. The CLI includes them in the build according to its configuration. This lets you keep a resource name in the code while its physical location changes when packaged. The [Resources](/en/resources) guide explains their use.

## Generated artifacts

When building and preparing distributions, `build/`, `release/`, and `.qyro/` appear. They are tooling outputs, separate from the code and input data. If you need additional build options, the CLI can read `build.json` at the root.

Version your code, public configuration, and assets; exclude secrets and generated artifacts in your project's `.gitignore`. Store user preferences or documents in an appropriate writable location, separate from installation resources.

Continue with [Build, bundle, and distribution](/en/tooling) to complete the CLI guide.
